**Date:** 2026-05-06
**Status:** approved (inline brainstorm)
**Worktree:** `worktrees/sp-3.5/`
**Branch:** `sp-3.5/main`

## 1. Problem

Three traps in the SP-5 trap stack consume fields that are currently always
`None`:

- `funding_rate_decay` — fires SHORT when `context.funding_rate < -0.001`
- `borrow_rate` — fires SHORT when `context.borrow_rate_pct > 50.0`
- `short_squeeze_cascade` — combines OI delta + funding for a SHORT veto

[backend/app/core/predictor.py:359-369](backend/app/core/predictor.py#L359-L369)
hard-codes `funding_rate=None`, `open_interest_delta_24h=None`,
`borrow_rate_pct=None` with a TODO pointing at SP-3.5. Net effect: those three
traps never fire, so any genuine "shorts paying to chase a falling knife" or
"capitulation squeeze in progress" setup goes uncaught and a bad SHORT slips
into PAPER.

Two Tab 1 panels scaffolded by SP-6 still show the "no data" placeholder:
[OiFundingRate.tsx](frontend/src/Tab1/sections/OiFundingRate.tsx) and
[IntermarketAnalysis.tsx](frontend/src/Tab1/sections/IntermarketAnalysis.tsx).
The user can't see funding pressure or DXY/gold correlation context that the
spec calls for.

## 2. Goal

Wire real funding rate + open-interest data from Binance Futures into
`TrapContext` so the two high-impact traps (`funding_rate_decay`,
`short_squeeze_cascade`) start firing on real data, populate the two Tab 1
panels with live values, and surface DXY/gold rolling correlations on the
IntermarketAnalysis panel using the existing yfinance adapter.

Borrow rate stays `None` for v1 (see §6 decisions).

### 3.2 New table: `intermarket_snapshots`

Migration `0014_intermarket`:

```sql
CREATE TABLE intermarket_snapshots (
    id BIGSERIAL PRIMARY KEY,
    symbol TEXT NOT NULL,
    captured_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    funding_rate DOUBLE PRECISION,
    mark_price DOUBLE PRECISION,
    open_interest DOUBLE PRECISION,
    source TEXT NOT NULL CHECK (source IN ('binance_futures', 'bybit'))
);
CREATE INDEX intermarket_snapshots_symbol_ts_idx
    ON intermarket_snapshots (symbol, captured_at DESC);
```

SQLite mirror (test fixture): same columns, `captured_at` as TEXT, no `DEFAULT NOW()`.

Retention: 14 days (cleanup task identical to SP-9 news cleanup pattern, but
nightly at 04:30 UTC to avoid clashing with the news cleanup at 04:00).

### 3.3 New adapter: `BinanceFuturesIntermarketAdapter`

`backend/app/data/adapters/binance_futures_intermarket.py`:

```python
class BinanceFuturesIntermarketAdapter:
    """Fetches funding rate + OI snapshot for a single symbol."""

    name: str = "binance_futures"

    async def fetch_snapshot(self, symbol: str) -> IntermarketSnapshot | None:
        # GET /fapi/v1/premiumIndex?symbol=BTCUSDT → funding_rate + mark_price
        # GET /fapi/v1/openInterestHist?symbol=BTCUSDT&period=5m&limit=1
        #   → openInterest at most-recent 5m bucket
        # Combine and return.
```

Symbol mapping: spot `BTC/USDT` → futures `BTCUSDT` (drop the slash). Same
mapping is already used by `BinanceAdapter` in SP-3.

Rate-limit: piggyback on the existing
`RateLimitedClient` pattern from SP-3 (Binance 2400 req/min weight bucket).
Each snapshot is 2 requests, top-30 universe = 60 requests every 5 min = 720
req/hr — negligible.

### 3.4 New worker: `intermarket_worker`

`backend/app/data/intermarket_worker.py` follows the SP-9 news-worker pattern
exactly:

- `start_intermarket_snapshot_task(session_factory)` — every 5 min loop
- `start_intermarket_cleanup_task(session_factory)` — nightly 04:30 UTC,
  delete rows older than 14 days
- Both gated in `app.main.lifespan` by `env not in {test, ci} AND
  worker_enabled`

Worker logic per tick:

1. Read top-30 universe from `asset_universe` (existing SP-3 table)
2. For each symbol: `await adapter.fetch_snapshot(symbol)`
3. Bulk INSERT all results into `intermarket_snapshots`
4. Sleep 300s

### 3.6 New REST endpoint

`GET /api/v1/intermarket/{symbol}` returns:

```typescript
{
  symbol: "BTC/USDT",
  funding_rate: -0.0012,           // null if no snapshot yet
  mark_price: 78320.5,
  open_interest: 1.23e9,
  open_interest_delta_24h_pct: 0.085,  // +8.5% in 24h
  dxy_correlation_30d: -0.42,      // null if Yahoo data unavailable
  gold_correlation_30d: 0.18,
  captured_at: "2026-05-06T14:55:00Z"
}
```

Correlations: rolling 30-day Pearson on daily close % changes between the
symbol (via `BinanceAdapter`) and SPX/DXY/GOLD via the existing
`YahooAdapter` (SP-3). Computed at request time, cached 1h in Redis.

### 3.7 Frontend wire-up

  open_interest + 24h delta bar. Color: green if funding ≥ 0, red if
  negative.
- **IntermarketAnalysis.tsx** — replace "no data" branch with two correlation

## 6. Decisions

| # | Question | Resolution |
|-|-|-|
| 1 | Source: Binance only or Binance + Bybit cross-check? | **Binance only for v1.** Bybit adapter for cross-check is a known follow-up if real-money trading reveals divergence. |
| 2 | Borrow rate source? | **Skip for v1, `borrow_rate_pct=None` permanently.** Binance margin borrow is account-specific (needs API key); public sources are flaky. The `borrow_rate` trap is the lowest-impact of the three; the other two cover the real risk. Documented as known gap. |
| 3 | Snapshot cadence? | **5 min.** Funding rate updates every 8h on Binance (so 5min over-samples) but mark/OI move continuously. Matches news worker cadence. ~720 req/hr against 144000/hr quota → 0.5%. |
| 4 | Correlation pairs? | **DXY (`^DXY`) + Gold (`GC=F`) via yfinance.** SPX is a third candidate but the IntermarketAnalysis spec calls for "intermarket" not "intra-equity"; SPX deferred. |
| 5 | Correlation window? | **30 daily bars.** Standard for crypto-vs-macro correlation analysis; matches the panel label "30d". |
| 6 | Where does `_build_trap_context` live? | In `predictor.py` (alongside `_build_news_summary` from SP-9). Keeps the predictor file as the single integration point. |
